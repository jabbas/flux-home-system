# Migracja patchy bootstrapu na format Talos 1.14 — design

Data: 2026-09-06
Status: zatwierdzony, gotowy do planu wdrożenia

## Cel

Przywrócić działanie bootstrapu po podbiciu `talosctl` do 1.14.0. Wszystkie patche
machine configu przechodzą na natywne dokumenty 1.14, tak żeby wygenerowany config
nie zawierał ani jednego pola legacy i nie wywoływał żadnego ostrzeżenia
deprecacyjnego.

Zakres obejmuje **wyłącznie pliki repozytorium**. Żywy klaster pozostaje nietknięty —
nadal chodzi na Talosie 1.13.5 z konfiguracją w starym formacie i to jest w porządku.

## Kontekst: dlaczego bootstrap przestał działać

`bootstrap/site.yaml` pinuje Talosa **1.14.0**, a lokalny `talosctl` został podbity do
tej samej wersji, żeby świeży bootstrap stawiał najnowszego Kubernetesa (decyzja
właściciela: bootstrap ma zawsze instalować najnowszy K8s). Podbicie klienta osiągnęło
cel — `gen config` daje teraz kubelet i control plane w wersji **1.37.0** oraz kontrakt
configu v1.14 — ale jednocześnie ujawniło, że rola `initialize_talos_configuration` jest
napisana pod format 1.13.

Talos 1.14 rozbił monolityczny dokument `v1alpha1` na około trzydzieści osobnych
dokumentów. Pola takie jak `cluster.allowSchedulingOnControlPlanes`, `cluster.apiServer`,
`machine.install`, `machine.network.nameservers` i `machine.nodeLabels` **nie istnieją już
w schemacie `v1alpha1`**. Parser nadal je przyjmuje ze względu na kompatybilność, ale
walidator odrzuca config, bo odpowiedni dokument już zawiera tę konfigurację.

Skutek zmierzony `talosctl validate -m metal`: **pięć z dziewięciu patchy nie przechodzi**.

| Patch | Objaw |
|---|---|
| inline `machine.install.image` | `UnattendedInstallConfig config is incompatible with v1alpha1 config (.machine.install)` |
| `allow-scheduling.yaml` | `.cluster.allowSchedulingOnControlPlanes is already set in v1alpha1 config` |
| `kube-apiserver-resources.yaml` | `kube-apiserver config is already set in v1alpha1 config` |
| `oidc.yaml` | jw. + `WARNING: .machine.files is deprecated` |
| `remove-externallb-label.yaml` | **twardy błąd `talosctl apply`**, nie walidacji — patrz niżej |
| `ntp.yaml`, `sysctls.yaml`, `registry-home.yaml` | przechodzą |

`remove-externallb-label.yaml` jest najgorszym przypadkiem, bo pada wcześniej niż
walidacja: `machine.nodeLabels` już nie istnieje, więc `$patch: delete` nie ma czego
usunąć i `talosctl apply` wywala się z `lookup failed`.

## Odrzucona alternatywa: `--talos-version v1.13`

Klient 1.14 potrafi wygenerować config w starym kontrakcie. Zweryfikowano: wtedy
**wszystkie osiem patchy plus inline przechodzi bez żadnych zmian**, a bootstrap działa
od ręki.

Odrzucone, bo furtka nic nie kupuje poza odroczeniem:

- **nie zmienia wersji Kubernetesa** — nadal 1.37.0, bo `--talos-version` steruje
  wyłącznie kontraktem machine configu
- **nie zmienia obrazu instalatora** — nadal `:v1.14.0`
- `machine.files` już dziś wypisuje ostrzeżenie deprecacyjne
- helm opisuje flagę jako „backwards compatibility" — to ścieżka wyjścia, nie docelowa
- nie chroni przed najgorszym błędem: `remove-externallb-label` i tak wywala `apply`

Pozostaje jako **awaryjny rollback**, gdyby migracja okazała się zablokowana. Wtedy
trzeba dołożyć `--kubernetes-version` pod wersję zgodną z Talosem 1.13.

## Rozwiązanie

### Zmiana w roli

`talosctl gen config` w zadaniu generującym config dostaje dwie flagi:

```
--install-image factory.talos.dev/metal-installer/{{ talos.schematic_id }}:v{{ talos.version }}
--with-examples=false
```

`--install-disk /dev/vda` **zostaje** — bez niej domyślnym dyskiem jest `/dev/sda`, co
dla VM na Proxmoksie z virtio jest złym dyskiem. W 1.14 flaga nie ustawia już
`machine.install.disk`, tylko `UnattendedInstallConfig.provisioning.diskSelector.match`
w postaci wyrażenia CEL `disk.dev_path == "/dev/vda"`.

**Inline patch na `machine.install.image` znika z zadania `Apply patches`.**

Powód nie jest kosmetyczny. Zmierzono: **każdy patch celujący w `UnattendedInstallConfig`
kasuje `provisioning.diskSelector`** — również patch zawierający wyłącznie
`installer.image` i nietykający sekcji `provisioning`. Zachowanie jest niespójne
(`wipe` przeżywa, `diskSelector` nie), co wskazuje na bug round-trippingu wyrażeń CEL.
Skutek byłby `UnattendedInstallConfig: provisioning.diskSelector.match is required`.

Nie patchujemy tego dokumentu wcale, więc problem nie występuje. Gdyby kiedyś zaszła
potrzeba nadpisania obrazu per node, patch musiałby powtórzyć `diskSelector` i `wipe`.

`--with-examples=false` to czysta kosmetyka: usuwa 54 linie zakomentowanych przykładów.
Zweryfikowano, że flaga **nie ma** związku z konfliktami — różnica między `true` i `false`
to wyłącznie komentarze, zero aktywnej konfiguracji.

### Docelowa forma patchy

Wszystkie zwalidowane `talosctl validate -m metal` w pełnym zestawie ośmiu.

**`allow-scheduling.yaml`** — `allowSchedulingOnControlPlanes` nie ma następcy jako pole;
odpowiednikiem jest zdjęcie taintu.

```yaml
apiVersion: v1alpha1
kind: KubeNodeConfig
taints:
    node-role.kubernetes.io/control-plane:
        $patch: delete
```

**`remove-externallb-label.yaml`**

```yaml
apiVersion: v1alpha1
kind: KubeNodeConfig
labels:
    node.kubernetes.io/exclude-from-external-load-balancers:
        $patch: delete
```

**`kube-apiserver-resources.yaml`** — merge zachowuje `image` i `certExtraSANs` z bazy.

```yaml
apiVersion: v1alpha1
kind: KubeAPIServerConfig
resources:
    requests:
        cpu: 200m
        memory: 512Mi
    limits:
        memory: 2Gi
```

**`nameservers.yaml`** — `nameservers` to teraz lista obiektów, nie lista stringów. Merge
zachowuje `hostDNS` z bazy.

```yaml
apiVersion: v1alpha1
kind: ResolverConfig
nameservers:
    - address: 10.1.255.2
    - address: 1.1.1.1
```

**`ntp.yaml`** — dokument nie występuje w bazie, powstaje od zera.

```yaml
apiVersion: v1alpha1
kind: TimeSyncConfig
ntp:
    useNTS: false
    servers:
        - 10.1.255.2
        - time.cloudflare.com
        - pool.ntp.org
```

**`sysctls.yaml`** — `params` to `map[string]string`; wartość liczbowa jest koercjonowana
do stringa bez utraty precyzji, ale forma kanoniczna to string.

```yaml
apiVersion: v1alpha1
kind: SysctlConfig
params:
    user.max_user_namespaces: "1048576"
```

**`registry-home.yaml`** — dokument nazwany, merge po polu `name`.

```yaml
apiVersion: v1alpha1
kind: RegistryTLSConfig
name: registry.home
ca: |-
    -----BEGIN CERTIFICATE-----
    <pełny PEM jabbas-ca>
    -----END CERTIFICATE-----
```

**`oidc.yaml`** — największa zmiana merytoryczna, i zarazem uproszczenie.

Talos 1.14 **jawnie blokuje** stare flagi:
`kube-apiserver extra argument "oidc-issuer-url" is not allowed: use KubeAuthenticationConfig`.
Do tego `KubeAPIServerConfig` **nie ma pola `extraVolumes`** — w całym drzewie
dokumentacji 1.14 nie istnieje żaden mechanizm montowania pliku z hosta do statycznego
poda control-plane.

Stary mechanizm nie ma więc następcy i nie jest potrzebny: CA idzie **inline**. Znika
`machine.files` z 55-linijkowym PEM-em wypychanym na dysk noda, znika hostPath
`/var/certs`, znika mount w statycznym podzie i cztery flagi `oidc-*`. Całość zwija się
do jednego dokumentu.

```yaml
apiVersion: v1alpha1
kind: KubeAuthenticationConfig
configuration:
    anonymous:
        enabled: true
        conditions:
            - path: /livez
            - path: /readyz
            - path: /healthz
    jwt:
        - issuer:
            url: https://authentik.dev.home/application/o/talos-cluster/
            audiences:
                - talos-cluster-id
            certificateAuthority: |
                -----BEGIN CERTIFICATE-----
                <pełny PEM jabbas-ca>
                -----END CERTIFICATE-----
          claimMappings:
            username:
                claim: preferred_username
                prefix: ""
            groups:
                claim: groups
                prefix: ""
```

### Stan końcowy dokumentu `v1alpha1`

Po migracji zostaje w nim wyłącznie to, co w 1.14 nadal do niego należy:

```yaml
version: v1alpha1
machine:
    type, token, ca, certSANs, features.diskQuotaSupport
cluster:
    token, etcd.ca
```

Zero pól legacy, zero ostrzeżeń deprecacyjnych z walidatora. To jest wartość, której
furtka `--talos-version v1.13` by nie dała.

## Pułapki formatu wielodokumentowego

Cztery zachowania, których w monolicie nie było. Każde zweryfikowane eksperymentalnie.

**Pola `Unstructured` są podmieniane w całości, nie merge'owane.** Dotyczy
`KubeAuthenticationConfig.configuration` (oidc) oraz `KubeAPIServerConfig.resources`.

Konsekwencja krytyczna: **blok `anonymous` musi być powtórzony w patchu OIDC**. Bez niego
`/livez`, `/readyz` i `/healthz` przestają być dostępne anonimowo. Walidacja tego
**nie wykryje**, bo zawartość `Unstructured` nie jest sprawdzana semantycznie — config
przechodzi wszystkie bramki, a klaster nie wstaje poprawnie.

**Format CA zmienia kodowanie.** Stare `machine.registries.config.<host>.tls.ca`
przyjmowało **base64 z PEM-a**, nowe `RegistryTLSConfig.ca` przyjmuje **goły PEM**.
Wklejenie base64 do nowego pola to najłatwiejsza cicha awaria w tej migracji — to zwykły
string, więc walidator prawdopodobnie go przepuści.

**Listy się doklejają, nie zastępują.** Dwukrotne nałożenie `nameservers` daje
`[10.1.255.2, 1.1.1.1, 10.1.255.2, 1.1.1.1]`, a config nadal jest „valid". To samo dotyczy
`TimeSyncConfig.ntp.servers`. Playbook regeneruje config przy każdym przebiegu przez
`gen config --force`, więc jest bezpiecznie — ale **te patche nie nadają się do
`talosctl patch` na żywym nodzie**.

**`$patch: delete` nie jest idempotentny.** Ponowne nałożenie `allow-scheduling` na
config, który ma już zdjęty taint, wywala się twardo z `lookup failed`. Paradoksalnie to
zachowanie lepsze niż ciche doklejanie list — dowiadujesz się natychmiast — ale wiąże oba
patche `KubeNodeConfig` ze świeżo wygenerowanym configiem.

Ta sama przyczyna sprawia, że `allow-scheduling` **nie zadziała na `worker.yaml`** (worker
nie ma taintu control-plane). Dziś nieistotne, bo playbook aplikuje wyłącznie
`controlplane.yaml` na wszystkie trzy nody. Gdyby doszły workery, oba patche
`KubeNodeConfig` trzeba ograniczyć do control-plane.

## Decyzje projektowe

**`allow-scheduling` i `remove-externallb-label` zostają jako dwa osobne pliki**, mimo że
oba celują w `KubeNodeConfig`. Zweryfikowano, że scalenie działa i daje semantycznie
identyczny wynik, więc to wybór stylistyczny, nie techniczny. Argumenty za rozdzieleniem:
nazwy plików są dziś jedyną dokumentacją *intencji* (`kube-node.yaml` mówiłby tylko,
w co celuje, nie po co); to dwie niezależne decyzje, z których jedna może kiedyś odpaść
bez drugiej; lista `-p @patch/…` w playbooku pozostaje 1:1 zgodna z dzisiejszą, więc diff
migracji ogranicza się do treści plików.

**`useNTS: false` jawnie**, mimo że pominięcie pola też przechodzi walidację. NTS
domyślnie włącza się, gdy konfiguracja nie jest podana, a przy włączonym NTS wszystkie
serwery muszą być hostname'ami — `10.1.255.2` zostaje wtedy odrzucone przez walidator.
Dziś ratuje nas niepisana implikacja, że podanie `ntp.servers` liczy się jako podanie
konfiguracji. Jedna zmiana defaultu w przyszłej wersji i OPNsense wypada z synchronizacji
czasu. Jedna linia usuwa całą klasę problemu.

**Zakres kompleksowy, nie minimalny.** `ntp.yaml` i `sysctls.yaml` działają dziś
poprawnie i bez ostrzeżeń, ale migrujemy je razem z resztą. Decyzja właściciela; koszt
jest niski (oba dokumenty powstają od zera, więc nie ma ryzyka zgubienia czegoś przy
merge'u), a zysk to jeden przebieg zamiast dwóch przy następnym wydaniu Talosa.

## Weryfikacja

Bramką jest pełny przebieg end-to-end, nie walidacja pojedynczych patchy:

1. `talosctl gen config` z nowymi flagami
2. wszystkie osiem patchy naraz, w kolejności z playbooka
3. `talosctl validate -m metal` → `valid`, **zero ostrzeżeń**

Do tego weryfikacja **intencji**, nie tylko poprawności: dla każdego patcha trzeba
potwierdzić, że jego efekt jest obecny w finalnym configu. Walidacja mówi „config jest
poprawny", nie „config robi to, co chciałeś" — a przy polach `Unstructured` i przy
`$patch: delete` te dwie rzeczy potrafią się rozjechać.

Kolejność patchy nie ma znaczenia semantycznego. Przebieg w kolejności odwrotnej daje
config różniący się wyłącznie pozycją nowo utworzonych dokumentów; zawartość identyczna.

## Znane ryzyko

**`KubeAuthenticationConfig` nie jest weryfikowalny offline.** Pole `configuration` jest
typu `Unstructured`, więc `talosctl validate` sprawdza wyłącznie, czy YAML się parsuje.
Semantykę `AuthenticationConfiguration` zweryfikuje dopiero kube-apiserver 1.37 przy
starcie; `--dry-run` też jej nie złapie, bo używa tej samej walidacji.

Objaw przy błędzie: **apiserver nie wstaje po odbudowie klastra**. Miejsce do sprawdzenia
w pierwszej kolejności: logi statycznego poda kube-apiserver, sekcja
`AuthenticationConfiguration`.

Ryzyko przyjęte świadomie (decyzja właściciela). Uzasadnienie: zmiana jest czysto
deklaratywna, żywy klaster nie jest jej poddany, a bootstrap i tak nie był weryfikowany
od miesięcy — dopiero 2026-09-06 wyszło, że nie działał w ogóle z powodu brakującego
`secrets.yaml`. Test na jednorazowej maszynie ma sens jako osobny projekt „zweryfikujmy,
że bootstrap działa od zera", a nie jako przypis do tej migracji.

**Nieweryfikowalne offline pozostają też:** czy `useNTS` bez jawnego `false` faktycznie
zostaje wyłączone w runtime (stąd jawne `false`), oraz czy `RegistryTLSConfig` daje pełną
parytetowość z `machine.registries.config` dla zota — jedynym prawdziwym testem jest
realny pull z `registry.home` na nodzie.

## Poza zakresem

**Deduplikacja `jabbas-ca`.** Po migracji ten sam certyfikat występuje w dwóch patchach
(`oidc.yaml`, `registry-home.yaml`), tym razem w tym samym formacie PEM — więc
przynajmniej da się je porównać `diff`em zamiast oczami. Naturalnym rozwiązaniem jest
generowanie obu z jednego `ca.pem` przez `lookup('file', …)`, ale to zmiana w roli
Ansible, nie w patchach.

**Migracja żywego klastra** na Talosa 1.14 i na nowy schematic. Wymaga
`talosctl upgrade` z rebootem każdego węzła; rekomendowana ścieżka to
1.13.5 → 1.13.10 → 1.14.0. Właściciel wykona ją w przyszłości.

**Dryf `machine.install.image` na żywych nodach** (deklarują vanilla
`installer:v1.12.6`). Osobna, znana zaległość.

**`RegistryMirrorConfig` / pull-through cache**, `ImageCacheConfig`,
`RegistryAuthConfig` — dokumenty istnieją, ale nic ich dziś nie potrzebuje.
